# BH filter preview host

The launcher's **Preview Filter** used to send the filter to FilterBird, a separate web
reimplementation of BH's loot-filter rules. FilterBird drifts every time BH changes.
This folder replaces it: `BHPreviewHost.exe` loads the **installed `BH.dll`** into a
mock Diablo II and asks BH itself what it would display for each item.

## How it works

BH never checks that it is running inside the real game. It finds every game function and
variable with `GetModuleHandle("D2CLIENT.dll") + offset` or `GetProcAddress(module, ordinal)`
(`Patch::GetDllOffset`), reads the game version from `Game.exe`, and hooks the game by
writing `call`/`jmp` instructions at fixed offsets. The host provides all of that:

1. **Fake modules** (`PeShell.cpp`, `MockGame.cpp`): for each game DLL BH uses, the host
   writes a code-free DLL named `D2CLIENT.dll`, `D2COMMON.dll`, ... into a sandbox folder
   and loads it. Each has one big read/write/execute section and an export table with every
   ordinal BH imports. When the install's real DLLs are present, the fake module also copies
   their image size and full export list, so a BH build that uses a symbol the table below
   does not know still finds a (logging) stub instead of a null pointer.
2. **Symbol table** (`generated/D2Exports.g.h`): generated by `tools/gen_d2exports.py` from
   BH's own `D2Ptrs.h` and every `new Patch(...)` in BH's sources: 178 functions, 82
   variables, 55 code addresses and 36 patch sites at the time of writing, with calling
   convention and argument size for each function.
3. **Functions**: every function gets a stub at its exact offset. 67 that BH's item
   code relies on are real implementations (`D2Impl.cpp`): stats, item tables, item types,
   level requirements, sockets, string tables, player and area lookups and so on. All the
   others log their first call and return a configurable value (0 by default), popping the
   right number of argument bytes. Implementations are checked against BH's declared
   convention and argument size when installed, and refused if they disagree.
4. **Data** (`GameData.cpp`, `GameFiles.cpp`): item, item-type, stat, skill, unique, set,
   runeword, gem, affix and level tables are read from the install's own `.bin` files and
   string tables from its `.tbl` files (decoded as UTF-8, as the game does). The archives are
   read with the `StormLib.dll` PD2 ships in the install folder. PD2's own `Storm.dll` is the
   fallback: its `PD2_EXT.dll` import refuses to initialise outside the game, so a sandbox copy
   that imports `version.dll` instead is loaded, but its file lookups have not been seen to work. That data is laid
   out the way D2COMMON keeps it in memory (`sgptDataTable` and friends), including the name
   indices the game fills in at load time. Every table's record size is checked against BH's
   struct size.
5. **World** (`World.cpp`): one player in one area, plus the items being asked about, built
   from BH's own structure definitions (`D2Structs.h`).
6. **Driving BH** (`BHDriver.cpp`): copy `BH.dll`, `Game.exe` (only read, for the version),
   the user's `BH.json` and the filter into the sandbox, load BH, let its game thread "join
   the game", run one game-loop tick (which builds BH's rules), then for each item:
   - call the patched item-name site (`D2CLIENT+0x92366`) with the registers and stack the
     game uses there. That runs `Item::ItemNamePatch`, BH's real filter logic. An empty name
     means the filter hides the item.
   - call BH's exported `BHOnProperties` hook with the item selected. That is the text BH
     appends to the tooltip.

Nothing in BH is modified, and no game logic is reimplemented on the BH side. The mock only
stands in for the game.

## Mock values

Everything BH can read about the world has a default and can be changed per request
(`World.h`, `GameState`):

| Field | Default | Meaning |
|---|---|---|
| `character.class` | `1` (Sorceress) | 0 ama … 6 ass |
| `character.level` | `90` | `CLVL` |
| `character.stats` | `{}` | any other player stat, by id |
| `difficulty` | `2` (Hell) | `DIFF` |
| `area` / `act` | `109` / `4` | Harrogath, Act V |
| `defaultQuestFlag`, `questFlags` | `1`, `{}` | quest state |
| `defaultUiState`, `uiStates` | `0`, `{}` | open panels |
| `itemDiscoveryState` | `0xF` | PD2 discovery: everything discovered and owned |
| `itemStorageType` | `0` | PD2 storage type |
| `functionReturns` | `{}` | return value of **any** stubbed game function, by BH's name (e.g. `"D2CLIENT_GetMouseXOffset"`) |
| `variables` | `{}` | initial DWORD of **any** game variable, by BH's name (e.g. `"D2CLIENT_MouseX"`) |

Items (`ParseItemSpec`):

```json
{ "code": "uap", "quality": "unique", "fileIndex": 12, "itemLevel": 85,
  "flags": ["identified", "ethereal"], "sockets": 2, "runeword": 30,
  "prefixes": [0,0,0], "suffixes": [0,0,0], "rarePrefix": 0, "rareSuffix": 0,
  "stats": [{ "stat": 7, "layer": 0, "value": 2560 }], "setStats": [],
  "price": 1, "levelRequirement": 62, "gameName": "override" }
```

Stat values are raw game values (for example life is shifted left by 8, as in the game).

## Protocol

```
BHPreviewHost.exe --install <PD2 folder> --sandbox <scratch folder> --filter <file>
                  [--bh <BH.dll>] [--data <extracted data>] [--filter-level N]
                  [--state <json>] [--log <file>]
BHPreviewHost.exe --selftest <scratch folder>
```

The host prints `{"ready":true,...}` once BH is loaded, then answers one JSON line per
request line on stdin:

- `{"id":1,"op":"evaluate","state":{...},"items":[...]}` returns
  `{"id":1,"items":[{"gameName","name","hidden","description","qualityColor","error"}],"messages":[...],"sounds":[...]}`
- `{"id":2,"op":"catalog"}` returns every item base, unique, set item and runeword in the installed data
- `{"id":3,"op":"describe"}` returns the archives opened and the current mock state

Names keep the game's `ÿc` colour codes and line order (bottom line first, as the game
stores them). `qualityColor` is the colour the game prefixes after BH's hook runs.

## Building

Requires Visual Studio 2022 (v143, Win32) and a BH checkout **at the commit the shipped
`BH.dll` was built from**:

```
git clone https://github.com/Project-Diablo-2/BH ..\BH        (next to this repository)
msbuild PD2Launcherv2.BHPreview\BHPreview.sln /p:Configuration=Release /p:Platform=x86
:: or point elsewhere: /p:BHSourceDir=C:\src\BH
```

The pre-build step reruns `tools/gen_d2exports.py` against that checkout (if Python is on
the PATH), so the symbol table always comes from the BH being previewed. The committed
`generated/D2Exports.g.h` records the BH commit it was generated from.

Ship `bin\Release\BHPreviewHost.exe` next to `PD2Launcher.exe`. The launcher looks for it
there first, then in the install folder. It also has to be added to the launcher's update
bucket.

## Status

Verified on Windows 11 (MSVC v143 build, PD2 install with the November 2026 `BH.dll`):
- `--selftest` passes.
- Against a real install and filter, BH loads, joins the mock game and answers `evaluate` and
  `catalog`: filter names and colours, hidden items, unidentified/ethereal/socketed items,
  runewords and BH's tooltip text all come from BH's own code.
- Every `.bin` table loads with a record size matching BH's struct, except `ItemStatCost`
  (324 bytes in the file, 348 in BH because BH adds trailing fields it never reads); the
  loader re-strides it.
- The launcher builds with the new preview UI.

Still unverified: how closely each result matches what the same filter shows in game.

With `--log`, every `default stub: <name>` line is a game function BH called that the mock does
not implement. The one seen so far is `D2COMMON_10592_GetWeaponAttackSpeed` (weapon tooltips),
whose return value BH maps through the game's weapon-speed tables. Crashes inside BH are logged
with the faulting `module+offset`, registers and likely return addresses.

Known gaps:
- Map icons, drop notifications and sounds (`ProcessItemPacketFilterRules`) are not driven
  yet. They need the item-packet path.
- Items are always on the ground; inventory, stash and vendor locations are not modelled.
- The game's own pre-filter names (`gameName`) are built by the mock from the string tables.
  Pass `gameName` to override one.
- `description` is only the text BH appends, not the game's own property lines.
